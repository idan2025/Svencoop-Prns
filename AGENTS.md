# AGENTS.md — Sven Co-op over Reticulum

## Project overview
Sven Co-op over Reticulum (Prns) — a bridge that tunnels Sven Co-op (GoldSrc, 32-bit) traffic over Reticulum (a peer-to-peer mesh networking layer). Players connect via RNS instead of direct UDP to the host.

## Repository structure
- `src/` — the bridge library (`sc-rns-bridge`): relay logic, client/server sessions.
- `controller/` — headless platform core (`sc-rns-controller`): orchestrates the bridge, the dedicated server (DS), steamcmd, game launch. No webview dependency — builds and runs headless.
  - `src/ds.rs` — DS manager: find/pull (steamcmd)/start/stop, background task for pulls, progress state.
  - `src/steamcmd.rs` — steamcmd runner: download bootstrap, pull app 276060, parse progress lines.
  - `src/controller.rs` — `BridgeController`: owns bridge session + DS manager + settings persistence.
  - `src/bin/web.rs` — headless web control panel (axum, port 8080) — Docker host entrypoint.
- `gui/src-tauri/` — Tauri v2 desktop shell (`sc-rns-gui`): thin wrapper over `BridgeController`, exposes commands to the frontend.
- `gui/dist/` — vanilla JS frontend (no bundler): `app.js`, `index.html`, `style.css`. Shared between the Tauri shell and the Docker web panel.
- `vendor/` — vendored Prns/Reticulum crates.
- `Dockerfile` + `docker-compose.yml` — Docker host release (web panel + bridge + DS in one container).

## Build commands
- Controller + bridge (headless): `cargo build --release --manifest-path controller/Cargo.toml --bin sc-rns-controller-web`
- Controller tests: `cargo test --release --manifest-path controller/Cargo.toml`
- Tauri desktop GUI: `cargo tauri build` (from `gui/src-tauri/`)
- Tauri GUI (no bundling): `cargo tauri build --no-bundle`
- Windows cross-build: `cargo build --release --target x86_64-pc-windows-gnu` (from `gui/src-tauri/`, needs `mingw-w64-gcc`, linker in `~/.cargo/config.toml`)
- Docker host: `docker compose up --build -d` (from repo root)
- AppImage: Tauri's `linuxdeploy` fails on CachyOS (strip `.relr.dyn` issue) — use `appimagetool` manually on the AppDir.

## Key conventions
- `DsStatus` uses `phase` (`idle`/`pulling`/`starting`/`running`/`error`), `progress_pct` (0-100), `last_line` (human-readable caption).
- steamcmd progress parsing: `parse_progress()` in `steamcmd.rs` — handles ANSI escape codes, format `progress: 92.78 (cur / total)`.
- DS download runs on a background task so the controller mutex isn't held; `status()` reads shared `Arc<Mutex<DsLive>>` lock-free.
- Bundle dir: portable mode prefers `sc-rns-data/` next to the executable (or `APPIMAGE` env var for AppImages); falls back to Tauri `app_data_dir`.
- Frontend `app.js` is transport-agnostic: Tauri `invoke` vs HTTP `fetch` (detected at runtime via `window.__TAURI__`).

## Known issues / gotchas
- Tauri `generate_context!` embeds the frontend brotli-compressed — `strings` can't find HTML content in the binary. Check `target/release/build/sc-rns-gui-*/out/tauri-codegen-assets/` for the embedded assets.
- Do NOT add the `protocol-asset` feature to `tauri` in `Cargo.toml` — `tauri.conf.json` has no `app.security.assetProtocol` config, and current `tauri-build` refuses to compile with a feature/allowlist mismatch ("The `tauri` dependency features ... does not match the allowlist"). Keep `features = []`. (An older note here said to restore this feature after builds — that's now wrong and will break the build; nothing in this app uses `convertFileSrc`/`asset:` loading, so the feature isn't needed.)
- Tauri's bundled `linuxdeploy` fails on CachyOS (`strip` can't handle `.relr.dyn` section). Workaround: let Tauri build the AppDir, then run `appimagetool` manually.
- steamcmd app 276060 anonymous login is flaky — "Missing configuration" / exit 8 errors are transient Steam-side issues, not code bugs. Retry succeeds.
- The DS (`svends_i686`) always binds `0.0.0.0` regardless of `-ip` flag — by design the container publishes 27015/udp unconditionally.
- An existing Sven Co-op install at `~/.local/share/Steam/steamapps/common/Sven Co-op/` will be found by `find_svends()` and reused (pull skipped).
- **`gui/dist/app.js` top-level code MUST stay wrapped in the `(function () { ... })();` IIFE.** WebKitGTK's Tauri webview can evaluate the inlined `<script>` block more than once during early load; a bare top-level `let`/`const` throws `Identifier '...' has already been declared` on the second pass. That SyntaxError gets reported to `window.onerror` as a content-less `Script error. @0:0` (looks like a cross-origin-muted error, easy to misdiagnose) and silently aborts all button/tab bindings after it — desktop-only, since the Docker web UI's browser doesn't re-evaluate the script. Symptom: buttons/tabs do nothing, no visible error, only reproduces in the Tauri desktop shell. The IIFE scopes the declarations per-invocation so a second pass can't collide. `app.js` also installs `window.addEventListener("error"/"unhandledrejection", ...)` that toasts any future uncaught error instead of failing silently — don't remove it.
- After editing `gui/dist/app.js` or `gui/dist/style.css`, re-run `python3 inline-assets.py` (regenerates `gui/dist/index.html` from the template) before `cargo build`/`cargo tauri build` — see build workflow gotcha above about touching `src/lib.rs` too.
- Rebuild ALL desktop artifacts after a `gui/dist/` fix, not just `target/release/sc-rns-gui`: `release/portable/sc-rns-gui` and `release/portable/*.AppImage` are separately copied/packaged and go stale independently (verify with `stat` — don't assume a fresh `cargo build` alone fixes what a user runs).
- **The Windows build needs `WebView2Loader.dll` shipped next to `sc-rns-gui.exe`.** It's a small (~160KB) loader stub every WebView2 app must carry itself — it is NOT part of the system-wide WebView2 Runtime install, so a bare copied `.exe` fails to launch on a real Windows machine with `WebView2Loader.dll ... not found` (confirmed by testing the actual exe under Wine — Wine surfaces this as a missing-DLL import error before you even get to Wine's own WebView2/DirectComposition limitations). It's built at `gui/src-tauri/target/x86_64-pc-windows-gnu/release/WebView2Loader.dll` alongside the exe — always copy it into any Windows distribution (the portable zip; never ship a bare standalone `.exe` release asset, it can't be self-contained). This bug shipped in v0.1.0 through v0.1.2 before being caught and fixed.
- Testing the Windows build from this Linux box: `wine gui/src-tauri/target/x86_64-pc-windows-gnu/release/sc-rns-gui.exe` (with `WebView2Loader.dll` in the same directory) gets you past the missing-DLL failure and as far as launching the real WebView2 runtime (installable under Wine via Microsoft's evergreen bootstrapper, `https://go.microsoft.com/fwlink/p/?LinkId=2124703` run under `wine ... /silent /install` — it genuinely installs). But WebView2's renderer process then crashes on Wine's incomplete DirectComposition support (`Unhandled page fault` in `dcomp:DCompositionCreateDevice`) — a real Wine limitation, not an app bug. So Wine can catch packaging bugs (missing DLLs, wrong paths) but can't validate that the UI actually renders; that still needs a real Windows machine.

- **DS is dual-tracked, not single-tracked**: `svends_run` (Linux) is a bash wrapper that spawns the real game binary (`svends_i686`) as a **plain child, not via `exec`** — so `DsManager`'s tracked child PID and the actual game process are different PIDs in a parent/child relationship. This has real consequences (see "DS process supervision" below).
- Full PRNS feature set is live (as of v0.1.3+): IFAC passphrase support (`IfacContext::derive`) on every interface type, UDP (point-to-point) and WebSocket interfaces alongside TCP, independent dual server+client sessions in one process, DS map list + live `changelevel` + `sv_cheats` toggle, live A2S query stats (player list, map, VAC) on the DS tab, server destination hash surfaced + copyable in the GUI, full settings persistence (server/client/DS/interfaces all survive a restart and re-populate the forms).

## DS process supervision (important — bit us three releases in a row)
- **Stopping the DS must kill the whole process group, not just the tracked PID.** Because `svends_run` spawns `svends_i686` as a plain child, `SIGKILL`ing only the wrapper's PID leaves the actual game server running, orphaned, and still bound to the port. Every subsequent "start" (including trying to change the map, before the live changelevel/map picker existed) would then crash-loop forever with `Sock_Open: WARNING: port: 27015 bind: Address already in use` against that orphan — while the *old* server kept right on serving the *old* map, invisible to the controller. Fixed in `ds.rs`: spawn with `#[cfg(unix)] cmd.process_group(0)` (puts the wrapper + all its descendants in one process group), and `stop()` kills that whole group.
- **Do not shell out to a `kill` binary to do this — use `libc::kill()` directly.** This project's own Docker image only has `kill` as a shell builtin; there's no standalone `/bin/kill` or `/usr/bin/kill`. `tokio::process::Command::new("kill")` fails to spawn (ENOENT) in that image — and if the error is discarded (`let _ = ...`), the "fix" silently does nothing in the one place it matters. This shipped broken in v0.1.7 and was only caught by testing a real stop/start cycle against the actual deployed container (a local `cargo test` passed fine, because the dev machine *does* have `/usr/bin/kill`). Fixed for real in v0.1.8 with a direct `libc::kill(-(pid as libc::pid_t), libc::SIGKILL)` syscall — no external binary involved, works regardless of what shell utilities a given container happens to ship.
- **General lesson from the above**: when a fix depends on what binaries/utilities exist in the environment, verify against the *actual target* (the Docker image, in this case), not just wherever `cargo test` runs locally. A green test on the dev machine is not proof the fix works where it's deployed.
- **DS stdin is a pipe that buffers even while nothing is reading it.** While `svends_run` is crash-looping (no live `svends_i686` yet), any `changelevel`/`sv_cheats` command sent via the API sits buffered in the OS pipe. The moment a real game process finally starts and reads stdin, it receives whatever was queued — which can look like a totally unrelated, seemingly random map change happening right at startup. If DS behavior looks confusing after a crash-loop, check for stale buffered commands as the explanation before assuming a new bug.
- Stock `mapcycle.txt` (as shipped by Sven Co-op itself, not this project) starts with `-sp_campaign_portal` — a single-player campaign-select hub screen, not a playable coop map. An empty server times out and rotates onto it. `fix_mapcycle_default()` in `ds.rs` strips that entry and promotes `svencoop1` to the front, running on every DS start (fresh install or existing) — self-healing, doesn't touch an already-customized cycle.

## Settings persistence gotchas
- `resume()` (called once on process boot) re-attaches every saved interface by calling the *same* `add_interface_tcp/udp/websocket/auto` methods the UI uses — and those used to unconditionally append a new descriptor to `settings.json` every time, **including during resume**. That meant a saved interface duplicated itself on every single container/app restart, compounding without bound (observed: 11 entries in production after a handful of restarts). Fixed: `add_interface_*` now go through `record_interface()`, which updates an existing descriptor in place instead of appending when one already matches on kind/role/addr/peer_addr; `resume()` also runs a one-time `dedup_interfaces()` cleanup pass on load, so an already-corrupted `settings.json` self-heals on its next restart without manual editing.
- **Recurring design pattern in this codebase**: when a config file/JSON can drift into a bad state from stock defaults or accumulated bugs, prefer a self-healing repair pass on load/start over a one-off manual fix. Used for: the GitHub release draft-reversion-on-tag-recreate (`gh release edit --draft=false` every publish run), `mapcycle.txt`'s stock bad default, and `settings.json` interface duplication. Follow this pattern for similar future bugs rather than a manual cleanup that only fixes the current instance.

## Release process
- GitHub: `idan2025/Svencoop-Prns`. CI: `.github/workflows/release.yml` — triggered on `v*` tag push, builds Linux (AppImage/ELF/deb/rpm)/Windows (native MSVC)/macOS (arm64+x86_64) + a `ghcr.io/idan2025/svencoop-prns` Docker image, then a `publish-release` job collects everything into one GitHub Release.
- **Version bump checklist** (all three, every release): `gui/src-tauri/tauri.conf.json` (`"version"` — this is what CI reads for artifact filenames), `gui/src-tauri/Cargo.toml` (`version = "..."`), then `cargo check` inside `gui/src-tauri/` to regenerate `gui/src-tauri/Cargo.lock` (also tracked in git, commit it too).
- **Tag-and-release flow**: commit → `git push origin main` → `git tag vX.Y.Z` → `git push origin vX.Y.Z`. This kicks off CI (~5 min). The `publish-release` job always creates the release **as a draft with auto-generated notes** on first creation for a tag — write real notes and un-draft with `gh release edit vX.Y.Z --repo idan2025/Svencoop-Prns --notes-file <path> --draft=false --title vX.Y.Z`. Re-running the same tag (re-uploading assets) self-heals any prior draft-reversion automatically (see CI's own `--draft=false` step), so this is only a manual step on first creation.
- Monitor a running release build with `gh run list --workflow=release.yml --limit=1 --json status,conclusion` (or the `Monitor` tool wrapping a poll loop) rather than guessing timing — takes ~5 min for the full matrix.
- Latest as of 2026-08-28 (end of session): **v0.1.8**.
- Artifacts per release: AppImage (~107MB), Linux ELF (~22MB), Windows portable zip (exe + `WebView2Loader.dll` + README — see Windows gotcha above, never a bare `.exe`), deb, rpm, portable archives, Docker image.
- Portable mode: `sc-rns-data/` folder next to executable stores all mutable state (settings, identities, steamcmd, ~2.74GB DS).
